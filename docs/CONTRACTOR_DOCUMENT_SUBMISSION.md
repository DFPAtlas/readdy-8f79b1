# Contractor document submission

Accepted workforce invitation links now offer private document submission. Each request is authorised against the stored token hash, invitation expiry/revocation, current worker email/status, the inviter's active company role and company write access. Company managers can revoke accepted links, and a new invitation supersedes previous pending and accepted links for that person.

Recipients can submit PDF, PNG, JPEG or WebP files, up to 5 MB each and 20 reservations per invitation. The server checks file signatures against the declared MIME type, chooses the actual worker/company and private storage path, and never overwrites an existing object. Deterministic submission ids allow retries with the same file and metadata, including recovery after an uncertain storage response. A completed submission creates a restricted workforce-document record marked awaiting review and an audit event attributed to the invitation link, not falsely to the inviting staff member. Company reviewers use the existing workforce document panel and signed-file access. They can accept/reject the document separately; no upload approves a worker for site work or grants workspace access.

The recipient list includes only records submitted through that invitation. It excludes storage paths, signed links, internal review notes and earlier office-held documents. Raw invitation tokens are not stored, logged or persisted in browser storage by this feature. Bank-detail documents are excluded. This is document collection for review, not full bank-data, insurance-record, qualification-record or payroll onboarding. File-signature checks are not malware scanning or validation of document contents.

## Deployment

Apply `20261025155351_contractor_document_submission.sql`, then deploy the `contractor-documents` Edge Function with entrypoint `index.ts` and relative dependency `handler.ts`. Its gateway JWT check is disabled because recipients need no staff account; the handler performs invitation-token authentication on each public action. The standard project-provided SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY stay server-only. No new email provider or sending secret is required by document submission.

Publish the frontend from the same commit after deploying the backend. It reuses `/workforce/accept#token=...` and legacy contractor invitation routes. Staff changes are on the workforce invitation page and the existing workforce-profile document panel. Demo files and email sending are unchanged.

The function also implements a server-authorised `cleanup` action. It removes unregistered staging objects only when their invitation has expired or been revoked and the reservation is older than a day, then removes the matching staging record. Registered documents are never selected. Failed cleanup remains retryable. Failed staging reservations count toward the invitation cap and can be resumed with the same file/metadata while the link is valid.

### Scheduled staging cleanup

Deploy the updated `contractor-documents` handler before applying `20261029090325_contractor_cleanup_schedule.sql` and `20261029090606_contractor_cleanup_extension_schema.sql`. These add `pg_net` in the extensions schema and an hourly database cron job, `contractor-document-staging-cleanup`, at minute 23 UTC. The follow-up reinstalls the newly added, non-relocatable extension without CASCADE before its first scheduled run; do not apply it while requests are pending. Each invocation handles at most 100 staging reservations using the existing cleanup rules. A storage or registration-deletion failure returns HTTP 503 and leaves the failed reservation retryable on a later run.

The migration generates a dedicated random 256-bit maintenance credential inside Postgres and stores it in Vault as `contractor_cleanup_token`. Only its hash is stored in the private RLS-protected configuration table. The handler validates the hash through a service-role-only SECURITY INVOKER RPC; the maintenance token cannot authorise uploads or other database operations. Existing service-key maintenance calls remain supported. No secret is committed or returned by setup. The scheduler command contains only a private, owner-only enqueue function, and browser users cannot invoke the private enqueue function or authorisation RPC. Hosted pg_net makes pending request headers readable to database-login roles; the dedicated credential is intentionally limited to staging cleanup. Do not grant untrusted users direct database login or expose the net schema through the Data API.

The Vault entry `contractor_cleanup_project_url` is specific to the BuildNerve deployment. Set it to the correct project URL when deploying another environment. To rotate the token, update its Vault value and `procurement_private.contractor_cleanup_config.token_hash` together in one transaction. Never print either token or decrypted request headers.

For a manual operational check, run `SELECT procurement_private.enqueue_contractor_document_cleanup();` as the database owner, note the request ID, then inspect only `id,status_code,content,timed_out,error_msg` from `net._http_response` for that ID. HTTP 200 with `{"removed":0}` confirms authentication and an empty cleanup run; it does not prove deletion of a real stored file. Cron success alone confirms enqueueing, not the HTTP result. Responses are retained by pg_net for about six hours. Inspect HTTP failures separately from `cron.job_run_details`. Disable the schedule with `SELECT cron.unschedule('contractor-document-staging-cleanup');` to stop future automatic invocations; existing customer upload flows are unaffected.
